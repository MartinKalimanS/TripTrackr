# F14 State sweep (every route: loading, empty, error; denial; no handler; Tier 3): as built

Branch `feat/f14-states` (from `feat/ui-stack`). Task T559 (FR-064, FR-066, FR-080 as amended by Q-11; research D5-14; UI-SPEC
section 9.3 and section 10; pictures `core/home-loading`, `home-offline`, `home-error`, `trips-loading`, `trips-err`,
`trip-loading`, `trip-err`, `trip-zero`, `more/states` and `more/permission-denied` inside it). Owner decision Q-11: a pictured
control without a capability is a coming-soon control (`ComingSoonButton` or `useComingSoon`): one toast, nothing else, no invented
data. Visibility posture of everything here: nothing new is read, stored or sent; the states only say what the traveller's own local
store already answered.

## What T559 asked, and what was found

The F1 to F13 screens were already built with a loading, an empty and an error state each (features 004 and 005), so the sweep
began with an inventory rather than a rebuild. The inventory below is the result; the guards then ran over every state of every
route. They found six gaps, all closed (section "Gaps closed"). Nothing that was already right was restyled.

## Deviations (and why)

- **The photo library has no denial screen.** The picture `states.png` draws "Photos access is off / Open Settings / Choose files
  instead", but the app never asks for a photographs permission: `launchImageLibraryAsync` is the system picker, which is itself the
  grant (Expo SDK 57 ImagePicker: "No permissions request is necessary for launching the image library"; research D-34;
  `app.config.ts` blocks the storage and media permissions). No state can occur in which the library is refused, so none was drawn:
  a screen for a state that cannot happen would claim something the app does not know (FR-080 "no invented data"). A picker that
  fails to open keeps its plain error with Dismiss ("Your photo library couldn't be opened. Please try again."), and "Add photos" is
  the retry. If the owner wants a Settings button on that error, it is one `PermissionState` call. **Question for the owner.**
- **Add a document, camera not yet allowed, stays a card.** Only the refusal is a `PermissionState` (C5-28 names the denial screens);
  the ask ("Allow the camera", "Allow camera") is a request, not a refusal, and was already right.
- **`PermissionState` Open Settings is a primary on Add a document.** The adapter's rule was "never a primary, the screen has its own";
  on that screen it has none until the camera can start, so a `primary` prop (default off) keeps exactly one primary there and the
  existing assertion ("Open Settings is the one primary") stands unchanged.
- **One existing assertion changed.** `document-screens.test.tsx` looked for the spinner's visible text "Loading the document"; the
  skeleton carries no text (FR-064, UI-SPEC 9.3), so it looks for the region's name instead. Nothing else in an existing test changed.
- **Errors without a Retry** (Home, Trips, the passport, the trip and its stops, expenses, notes, the add-expense sheet, Offline
  maps' list of cities): a live query has nothing to run again, so they say what happened and that the data is safe. The Photos list,
  Documents, a document, Offline maps' pack check and the two gates have a "Try again" because their reader can be run or mounted
  again. This was already so and is now in the table.
- **Countries "No countries yet"** names its next step in words ("Add a stop to a trip and its country appears here") and has no
  button: it shows at the full detent, where the "Plan a trip" button is hidden, and a second primary is not allowed.
- **Spinner states kept** where a skeleton shaped like the content would have nothing to be shaped like: the add-expense sheet while
  its trip is read ("Loading trip", then the form), the camera check, the document picture opening, the city picker's lists, the first
  sync and the local-store gates (their words are their content). Each is one announced `progressbar`.
- **A route that crashes** is the router's and Sentry's boundary (`Sentry.wrap` in the root layout), not a designed state: an
  `ErrorBoundary` export of the root layout would render outside the providers the adapters read. Not changed here; see "Open items".
- **Unresolved dynamic ids.** `test/fixtures/testid-unresolved-count.json` regenerated from 100 / 80 to 102 / 79 (two forwarding
  adapters: `Detail` and `PermissionState` `detailTestID`; one accessible name that now resolves). `node scripts/testid-baseline.mjs
--check test/fixtures/testid-baseline.json` reports parity; every new id is additive (`document-camera-denied`,
  `photos-camera-denied`, `trip-missing-back`, `document-missing-back`, `offline-maps-empty-back`, `document-view-skeleton`).
- **Delete account** (You) is a pictured control with a capability that is not built yet (`DELETE /me`, T188), but not a Tier 3
  capability: it was already visible, disabled and announced unavailable, and the source guard lets an inert handler stand on a
  `disabled` control. Left as is.
